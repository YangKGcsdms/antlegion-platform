# 协议 v3.0 对抗性审计：它能不能撑起共享世界状态（2026-08）

`protocol-v3-feasibility-2026-08.md` 用十二个隔离进程验证了「规范说的事情是否发生」。
这一份问的是另一个问题：**规范自己有没有说错**。

方法是把 §8 的不变量和 §9 的三条定理逐条当成待反驳的命题，构造它们禁止的状态，看实际
折出什么。可复现的探针在 `antlegion-bus/test/adversarial-v3.test.ts`（11 条，随 CI 跑）。

结论先放这里：

- **一个真漏洞**：Δ 被规定为「日志的属性」，却存在日志之外。它能在不追加任何事实的情况下
  撤销一个终态 —— 也就是 §9.3 存在的全部意义。已修（实现 + 规范，中英双版）。
- **一处规范自相矛盾**：§11.1 关于 `seq` 复用的两句话不能同时为真。已按实际行为与
  持久化策略的交互重写。
- **一处实现把仅供参考的状态当成了终局判据**：SDK 的 resolve 门用了 §8.4 的尾随分支。
  影响有界（保守拒绝），记录在案。
- **一处 CLI 静默失败**：`alctl` 吞掉不认识的 flag，`--bus` 写错日志还报成功。已修。
- **两条结构性边界不是 bug，是这笔交易的价钱**：读者代价无上界；`author` 无认证。
  两条都已在规范里写明，但它们决定了「能撑起多大的共享世界」这个问题的答案。

---

## 一、Δ 活在日志之外（真漏洞，已修）

### 1.1 命题冲突

§8.4 写着：

> **Δ is a property of the log, not of the reader.** A bus MUST publish Δ (§7.5)
> and every reader MUST fold with the published value.

§9.2 的定理 2 很小心，把确定性表述为 **(P, Δ)** 的函数。§9.3 的定理 3 没有：

> **Theorem 3 (absorption).** If `ownership(F)` over P returns `resolved(a)` or
> `dead`, then it returns the same value over every P′ ⊇ P.

但定理 3 的证明里用到了「循环读到 x 时的 `active` 集合」，而 `active` 每一步都被
`fact.recv ≤ c.recv + Δ` 过滤 —— 它是 Δ 的函数。两条定理对同一个参数的处理不一致，
而不一致的那一条正是智能体据以行动的那条。

### 1.2 反例

一段前缀，两个 Δ：

```
seq 1  _.claim    author agent-a  recv 1000
seq 2  _.resolve  author agent-a  recv 1900
```

| Δ | `ownership(F)` | 为什么 |
|---|---|---|
| 3600 | `resolved(agent-a)` | 到 resolve 时领取仍存活，胜出者是 agent-a，采信 |
| 60 | `open` | 到 resolve 自己的 `recv` 时领取已失效，没有胜出者可采信 |

没有追加任何事实，没有改写任何字节，`resolved` 变回了 `open`。这不是「延迟不是分歧」
（§9.2 的边界），是同一个前缀上的两个答案。

### 1.3 它为什么必然发生

实现里 Δ 来自 `ANTLEGION_CLAIM_TIMEOUT`，每次启动读一次，日志里没有任何记录。于是：

- 换个容器镜像的默认值、恢复一份备份、换个运维、起一个副本 —— 任何一次都会重折全部历史。
- 一台 `ANTLEGION_CLAIM_TIMEOUT=30` 跑了三个月的总线，`node dist/index.js` 不带环境变量
  重启一次，就变成 Δ=600 的日志：三个月里每一条超时重分派都被追认为「其实没超时」。
- 日志文件本身不携带自己的含义，所以「把 journal 拷到副本」这个 §11.3 明确允许的操作，
  正确性取决于运维记不记得当初那个数。

**这是 v3.0 相对 v2.0 修好一半的问题。** v2.0 里 Δ 是每个读者的旋钮；v3.0 把它收归日志、
要求总线发布、要求读者采用 —— 但没有要求日志**记住**它，于是把分歧从「读者之间」搬到了
「同一条日志的不同时刻之间」。

### 1.4 修法

让那句话对字节为真：

- 创世时把 Δ 写进 `<dataDir>/log-meta.json`（temp → fsync → rename → fsync dir）。
- 已存在的日志按记录值服务；给了不同 Δ 就**拒绝启动**（新增 M12），并把两个值、
  改法都打进一行错误里。不替运维做选择 —— 改一条活日志的 Δ 是有意的破坏性操作。
- 没有 meta 的旧日志采用当前值并记下来，所以升级不会砸掉现有部署。
- `ANTLEGION_CLAIM_TIMEOUT` 未设或非法时解析成 `undefined` 而不是 600。否则「没设」
  看起来就像「要求 600」，和每一条用别的 Δ 写成的日志相撞 —— 包括这个旋钮本来要造的那些。

规范侧：§8.4 加「Δ 对一条日志终身固定」+ 反例；定理 3 的前提补上「Δ 固定」并说明这个前提
是承重的；§11.1 加 Δ 的读取来源；§10.2 加 M12；§B 说明 Δ 在创世时定死。中英双版同步。
**向量零变化** —— 折叠语义没动，动的是「谁有权决定 Δ」。

## 二、§11.1 的 `seq` 自相矛盾（规范已订正）

原文相邻两句：

> `seq` 恢复为出现过的**最大** `seq`。
> 总线 MUST NOT 复用 `seq`，永远不，包括在一次截断或修复之后。

撕裂的尾部记录被截断掉之后，出现过的最大 `seq` 正好少一个，下一次追加就拿回了那个号。
探针确认实现就是这么做的（而代码注释还宣称它没有）。

这不是随便一个 bug，因为「`seq` 从不复用」是定理 1/2/3 的证明都要用的引理。但它也不是
无条件的错误 —— 它取决于持久化策略：

- 逐条 `fsync`：撕裂意味着崩溃发生在写入与 `201` 之间，没有客户端拿到过那个回执，
  重发那个号对所有人不可见。**规则在这里成立。**
- 放宽策略：`201` 可能已经为一段随后被撕掉的内容返回过。重发那个号 = 一个 `seq` 在两个
  读者眼里对应两段内容 = §9 要排除的那种分叉。**规则在这里不成立。**

规范原本只说放宽策略「改变了 `201` 的含义」，没说这个改变会一路延伸到它命名的那个 `seq`。
已按上面的分情况重写，并要求总线报告截断（`/info` 的 `truncated_at`，实现已有）。

## 三、SDK 用尾随分支做终局决定（有界，记录在案）

§9.3 写得很清楚：

> A reader MUST NOT make a terminal decision on a trailing `claimed` or a
> trailing `open`.

`ClientV2.resolve()` 在追加之前先读回折叠，若不是当前胜出者就抛错。这是个好设计 ——
它把「悄悄变成空操作」换成了「响亮报错」。但它查的那个状态正是尾随分支：没有更晚的事实
时，`active` 被 `now ≤ c.recv + Δ` 用**读者自己的钟**过滤。

后果是不对称的，而且方向是安全的那边：

- 客户端的钟快了 → 它拒绝发一条总线本会采信的 resolve（`recv` 是总线的，不是它的）。
  代价是一次误报，agent 需要重新领取。
- 客户端的钟慢了 → 它发出去，然后由总线的 `recv` 决定采不采信，和所有读者一致。

也就是说这个门只会**保守地拒绝**，不会错误地放行。探针把这一点钉住了：同一段前缀、同一个
Δ，把 `now` 从 `claim.recv` 移到 `claim.recv + 601`，SDK 的前置条件翻转；而把 resolve 真的
追加上去之后，任何 `now` 都折出 `resolved`。

没改行为 —— 改成不看尾随分支就等于取消这个门。记在这里是因为「你的完成能不能发出去取决于
你的钟」值得知道，尤其是 Δ 很小的部署。

## 四、`alctl` 静默吞 flag（实现，已修）

不是协议问题，但属于同一类失败：

```bash
alctl publish task.request '{"t":1}' --bus http://10.0.0.7:28090
# → {"id":"…","seq":6}   写进了 http://localhost:28090
```

`--bus` 根本不是一个 flag（地址只从 `ANTLEGION_BUS_URL` 读），而解析器把任何 `--xxx`
收进一个 map，不认识就丢掉。于是「对的事实写进错的世界」还退出码 0。

已修两处：加上 `--bus`，并把未知 flag 变成错误 + 列出真的 flag。这些 flag 决定事实落进哪条
日志、以谁的名义，是这个 CLI 里最不该被静默忽略的输入。

## 五、论证：它能不能撑起共享世界状态

「共享世界状态」如果要成立，需要五件事。逐条对账：

| # | 要求 | v3.0 | 依据 |
|---|---|---|---|
| 1 | 同一前缀 → 同一答案 | ✅（本轮修 Δ 之后才真正成立） | §9.2 定理 2；Δ 现在被日志钉住 |
| 2 | 新信息不撤销已定结论 | ✅ 对吸收态（`resolved`/`dead`） | §9.3 定理 3；非吸收态规范显式列出并说明理由 |
| 3 | 谁都能写，含义不由中心裁定 | ✅ | §2.2 信任边界；总线不判断含义，§10.1 的门全在读者侧 |
| 4 | 崩溃后能重建 | ✅ | §11.1；日志就是状态，派生索引是纯投影，无状态机可丢 |
| 5 | 读者代价有界 | ❌ **没有** | §8.0 要求完整前缀 + §11.2 禁止回收骨架 ⇒ 内存下界随日志年龄单调增长 |

第 5 条已经在上一轮补进 §2.3，作为「假设会发生、但不处理」的代价列出，并给了三条缓解手段
（增量折叠、派生状态检查点、按 subject 空间分日志）。这是诚实的处理方式，但它决定了答案的
形状：**v3.0 撑得起一个有界寿命或有界规模的共享世界，撑不起一个无限期增长的。**

还有第六件事，规范把它划在保护范围之外，而它恰恰是「共享」这个词的强度所在：

| | |
|---|---|
| **`author` 无认证** | §12.2 明说：`author` 完整性不受保护，§8.3 在没有传输层认证时为空。 |

这一条的后果比它的措辞看起来重。§10.1 的每一道折叠门 —— 只有作者能撤回自己的事实、
只有作者能 supersede 自己的事实、只有领取胜出者能 resolve —— 门上写的都是 `author`，
而 `author` 是自称的。对一个能写这条总线的对手来说，这些门全部形同虚设：它可以冒充任何人
撤回任何事实、resolve 任何领取。

上一轮的十二进程验证里，mallory 的四次越权全部「上了链但没被采信」—— 那验证的是**读者门控
按规范工作**，前提是 mallory 用自己的名字。它没有验证、也无法验证冒名。

所以精确的表述是：

> **在信任边界之内**（一张你信任的网、或 loopback），v3.0 撑得起共享世界状态，
> 而且它的保证是可证明的而不是运营性的 —— 互斥是全序的定理，不是锁。
> **在信任边界之外**，除了 §9.1 的排序结果（它不依赖 `author` 诚实），§8 的每一条
> 保证都是相对于 `author` 诚实的。

这不是隐藏的缺陷，规范自己在 §12.2 和 §12.3 第 2 条说了（「不要暴露一台未认证的总线，
在与未设密码的 Redis 完全相同的意义与程度上」）。但把它和 §10.1 的门表放在一起读，才看得清
它的分量：**门是给诚实的参与者防手滑的，不是给对手防越权的。**

### 5.1 还有一条要说清楚：单总线

§2.4 把「两个组件为同一条日志分配 `seq`」划出协议之外，§11.3 只允许只读副本和按世界分片。
这是内部一致的 —— `seq` 只在一条日志内有意义，跨日志没有序可折。代价是这条日志是单点：
它的可用性就是整个世界的可用性，而协议不提供分区下的可用性。对一个定位成「本地可嵌入
基础设施（Redis 形状）」的东西，这是正确的取舍；对一个想做跨地域协调的东西，这是硬边界。

## 六、判定

**协议本身站得住，有一个真漏洞，已修。** Δ 那条不是措辞问题：它能在不追加任何事实的情况下
撤销终态，而终态是这套东西里唯一允许智能体据以行动的东西。修完之后，§9.2/§9.3 的前提在
字节层面成立，而不只是在散文层面。

**规范的自我批评水准很高，这轮找到的问题集中在「说了但没落到实现」和「两句话不能同时为真」，
而不是「模型错了」。** §8.1 规则 4 那种主动承认「这道门保护不了寄存器里的事实，也不可能
保护」的写法，在协议文档里是少见的；这轮的三条订正是同一种性质的补完。

**它能撑起共享世界状态，条件是两条：信任边界之内，以及日志寿命有界。** 这两条都不是可以
靠改代码去掉的 —— 第一条要传输层认证（协议明确不做），第二条要么接受 O(N) 的读者代价，
要么按 subject 空间切成多个世界。把它们说清楚，比假装没有更有用。
